Design Plan
===========

Vision
------
Describe ingestion, do not require users to implement plumbing.

The project provides a small, Arrow-native boundary between external systems
and destinations. It favors explicit configuration, predictable behavior, and
a deliberately constrained abstraction surface over a general-purpose data
platform.

Core contracts
--------------

1. Arrow is the data contract
   - Connectors emit pyarrow.RecordBatchReader streams.
   - Targets consume those streams.
   - Framework-specific data structures must not cross the connector-target
     boundary.
   - Implementations should minimize conversions, copies, and full-stream
     materialization.

2. Connectors represent external systems
   - A connector represents one external system or file-based input.
   - The framework has no Source or Resource distinction.
   - Connector-specific protocol behavior, including cursor semantics, belongs
     to the connector rather than to a global framework state model.

3. Targets represent destinations
   - A target owns destination-specific loading behavior.
   - Targets expose the same Arrow-stream input contract regardless of the
     storage system.
   - Targets return operational load statistics, not framework data models.

4. Merge strategy is explicit
   - Every load declares a merge strategy.
   - The strategy set is append, replace, upsert, and SCD2.
   - Each target must reject strategies it cannot implement correctly.
   - State is retained only when required by the selected strategy.
   - Upsert is configured as a merge mapping with `strategy: upsert` and one
     or more `keys`.
   - Upsert replaces destination records whose key tuple matches an incoming
     record and retains destination records with no matching incoming key.
   - Incoming upsert keys must be non-null and unique within a load. Duplicate
     or null keys are rejected rather than resolved by an implicit ordering
     rule.
   - Upsert requires compatible source and destination schemas. A missing
     destination is initialized from the incoming stream.
   - SCD2 retains history by business key and uses explicitly configured
     version-boundary and metadata fields; it must not add hidden columns.
   - Version boundaries come from ordered source data, not ingestion time.
   - SCD2 versions only when configured business attributes change and
     requires deterministic source ordering.

Declarative configuration
-------------------------

Configuration describes how data moves from a connector, through optional
Arrow-preserving transformations, into a target. Configuration is not a
Pipeline runtime abstraction.

- Common HTTP behavior must be configurable: authentication, pagination,
  request parameters and headers, timeouts, retries, rate limits, and schema
  handling.
- The initial HTTP pagination model is offset-based, defined by offset and
  limit parameter names, page size, and a response total path.
- The initial HTTP authentication model is bearer tokens resolved from named
  environment variables. Bearer authentication owns the Authorization header.
- Authentication configuration contains credential references, never plaintext
  credentials. Credentials are resolved from named environment variables or a
  supported secret-provider integration.
- Future machine-to-machine authentication models may include API keys in
  headers or query parameters, HTTP Basic authentication, and OAuth 2.0
  client-credentials authentication with token refresh.
- Scheduled ingestion must run non-interactively.
- OAuth refresh tokens may be established through an out-of-band
  authorization-code or device flow. Credential bootstrap is separate from
  connector execution and stores resulting credentials through the configured
  secret mechanism.
- Custom request signing, mutual TLS, and SDK-specific authentication are not
  initial core capabilities, but may be added when they represent reusable
  connector requirements.
- New authentication models must represent broadly reusable HTTP patterns and
  preserve predictable, testable configuration semantics.
- Request reliability uses optional timeouts, bounded retries for transport
  failures and retryable HTTP responses, and exponential backoff.
- Schema handling defaults to strict projection: every declared field must be
  present with its declared primitive type; undeclared source fields are
  ignored; null is allowed only for nullable Arrow fields.
- Custom Python is an escape hatch for genuinely unusual APIs. If a common
  ingestion pattern requires custom code, the declarative model is incomplete.

Supported scope
---------------

The initial connector scope includes:

- local Parquet files;
- flat files, including CSV and JSON Lines;
- databases with ADBC support; and
- HTTP APIs.

Object storage is a location for file connectors, not a separate connector
category. Message queues and streams, CDC and replication protocols,
spreadsheets, and SDK-only integrations are outside the initial scope.

Targets must have a strong Arrow ingestion story. Candidate targets include
Parquet, DuckDB, Iceberg, Delta, and databases supported through ADBC, such as
Postgres and Snowflake. Standardized ADBC loading paths are preferred where
they provide the required destination behavior; destination-specific loading
is acceptable when necessary.

Parquet target layout
---------------------

- A single-file Parquet target treats its configured path as one local Parquet
  file.
- Single-file writes must publish atomically.
- Single-file append prioritizes data integrity over write efficiency. Because
  a Parquet footer finalizes file metadata, append creates a replacement from
  existing and incoming Arrow batches rather than modifying a file in place.
- Single-file targets are appropriate for modest datasets and infrequent
  appends; they are not intended to optimize repeated large appends.
- A future dataset-directory mode may append immutable Parquet fragments. It
  requires explicit policies for schema compatibility, publication,
  concurrency, and compaction.

State and cursors
-----------------

- State should be derived from destination data whenever possible.
- Incremental loading should use loaded data or values derived through
  declarative transformations.
- Transformations may create timestamps, version markers, hashes, or similar
  values required for incremental loading and merge strategies.
- The framework must not add hidden ingestion metadata columns to user data.
- Cursor is a first-class runtime concept with three distinct concerns:
  definition, position, and resolution.
  - A cursor definition declares the ordered source field or fields, comparison
    semantics, source request binding, optional initial boundary, and lookback
    policy.
  - A cursor position contains only the resolved progress values needed to
    resume a connector.
  - Cursor resolution obtains a position from destination data where possible,
    or from persisted source-protocol state only when that position cannot be
    derived.
- Connectors own cursor semantics. Targets provide the minimum destination
  query capability needed to derive configured cursor positions.
- The framework supports two cursor modes:
  - A destination-derived watermark is an ordered field tuple read from
    destination data. Connectors bind its values to source request parameters.
    Watermarks may use numeric or timestamp-like values.
  - An opaque source cursor is a source-defined continuation or delta token.
    It is persisted only when a source cannot be resumed from destination
    data.
- Cursor positions are resolved before a connector reads and advance only
  after the destination load succeeds. Failed or partial loads must not
  advance cursor state.
- A scalar watermark is correct only when it is strictly increasing and
  unique. Sources that can emit tied values require a lexicographically ordered
  tie-breaker or an explicit overlap-and-deduplication policy.
- Cursor support must not introduce a Pipeline, StateManager, or CursorManager
  runtime abstraction.

Transformations
---------------

- Transformations consume Arrow streams and emit Arrow streams.
- Polars may be used internally for normalization, casting, and
  transformations; it is not part of the public data contract.
- Declarative transformations cover selection, renaming, casting, deriving,
  and filtering.
- Complex business logic, analytical modeling, aggregation, and cross-dataset
  joins are outside the ingestion framework.

Abstraction boundaries
----------------------

The only runtime concepts are:

- Connector
- Cursor
- Arrow stream
- Target
- Merge strategy

The framework does not expose Pipeline, Flow, Stage, Source, Resource, Asset,
Dataset, Block, Node, or registry abstractions. Configuration may describe an
ingestion workflow, but the framework does not model that workflow as an
independent runtime object.

Operational boundaries
----------------------

- Orchestration belongs to systems such as Prefect, Dagster, Airflow, and
  Temporal, not to this framework.
- Auditing, lineage, and governance belong in destination metadata, lakehouse
  catalogs, table formats, and dedicated governance tools.
- The framework may emit logs, metrics, and load statistics for operational
  troubleshooting; these are not an auditing system.
