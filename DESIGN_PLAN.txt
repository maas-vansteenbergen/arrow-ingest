Design Goals

1. Arrow is the only data contract
   - Connectors emit Arrow.
   - Targets consume Arrow.
   - No framework-specific data structures.
   - Minimize conversions and copies.

2. Connector-first model
   - A connector represents a single external system.
   - Running a connector produces an Arrow stream/table.
   - No source/resource distinction.

Initial supported connector categories
   - Parquet files. Initial support reads local Parquet files as native Arrow
     batches.
   - Flat files, including CSV and JSON Lines.
   - Databases with ADBC support.
   - HTTP APIs.
   - Object storage is a location for file connectors, not a separate connector
     category.
   - Out of scope initially: message queues/streams, CDC and replication
     protocols, spreadsheets, and SDK-only integrations.

3. Declarative by default
   - Authentication, pagination, incremental loading, rate limits and schema handling should be configurable.
   - Common ingestion patterns should not require custom Python.
   - Initial REST pagination support is offset-based, configured by offset and
     limit parameter names, page size, and a response total path.
   - Initial REST authentication support is bearer tokens resolved from named
     environment variables.
   - Initial REST request customization supports static string headers and query
     parameters; bearer authentication owns the Authorization header.
   - Initial REST reliability support provides optional request timeouts,
     bounded retries for transport failures and 429/5xx responses, and
     exponential backoff.
   - Initial schema handling is a strict projection: every declared field must
     be present with a matching primitive type; undeclared source fields are
     ignored; null is allowed only for nullable Arrow fields.

4. Python as an escape hatch
   - Custom code is only for genuinely unusual APIs.
   - If common REST APIs require Python, the abstraction is incomplete.

5. Minimal state
   - Derive state from the destination whenever possible.
   - Store only irreducible protocol state (e.g. opaque cursors, delta tokens).
   - Avoid separate state stores where destination metadata is sufficient.

6. Arrow-native targets only
   - Support targets with a strong Arrow story.
   - Examples: Parquet, DuckDB, Iceberg, Delta, Postgres via ADBC, Snowflake via ADBC.
   - Reducing scope is a feature.
   - Initial DuckDB support writes a RecordBatchReader directly into a named
     table in a local database file. It supports replace only.

7. Loaders built around ADBC
   - Prefer standardized Arrow ingestion paths.
   - Avoid destination-specific loading implementations where possible.

8. Polars as implementation, not abstraction
   - Use Polars internally for schema normalization, casting and transformations.
   - Keep Arrow as the public contract.

9. Transformations are declarative and Arrow-preserving
   - Transformations operate on Arrow streams through Polars.
   - Transformations consume Arrow and emit Arrow.
   - Transformations do not introduce a new framework data model.
   - Common operations (select, rename, cast, derive, filter) should be declarative.
   - Complex business logic belongs outside the ingestion framework.
   - The goal is schema shaping and normalization for loading.
   - Analytical modelling, aggregations and cross-dataset joins are out of scope.

10. Orchestration is out of scope
   - Integrates with Prefect, Dagster, Airflow, Temporal, etc.
   - The framework is for ingestion, not workflow management.

11. Merge strategies as a first-class concept
    - append
    - replace
    - upsert
    - scd2
    - Only retain state required to implement these strategies.

12. Relentlessly small abstraction surface
    Core concepts:
      - Connector
      - Cursor
      - Arrow Stream
      - Target
      - Merge Strategy

    Explicitly avoid:
      - Source
      - Resource
      - Pipeline
      - Asset
      - Dataset
      - Block
      - Flow

13. Cursor philosophy

- State should be derived rather than stored whenever possible.
- Incremental ingestion should be based on loaded data or on columns derived through the framework's declarative transformation layer.
- Framework transformations may create timestamps, version markers, hashes, or other values needed to support incremental loading and merge strategies.
- Derived values are preferred over framework-managed metadata whenever they provide equivalent behavior.
- The framework must not add hidden ingestion metadata columns to user datasets.
- Opaque cursor persistence is a last resort for source protocols that expose irreducible state (for example continuation tokens or delta tokens).
- A cursor represents only the minimum irreducible state required to resume ingestion.
- Cursor semantics belong to connectors, not to the framework.

14. Pipeline as configuration, not abstraction

- Ingestion workflows are described declaratively in configuration.
- The framework does not expose Pipeline, Flow, Stage, Asset, Node, or Resource abstractions.
- Configuration describes how data moves from a Connector, through optional Arrow-preserving transformations, into a Target.
- Runtime concepts are limited to Connector, Cursor, Arrow Stream, Target, and Merge Strategy.
- The YAML represents the ingestion pipeline; the framework does not model a pipeline as an independent runtime object.

15. Auditing is out of scope

- The framework is responsible for ingestion, not governance.
- The framework does not maintain a system of record for load history, lineage, or auditing.
- Auditing should be derived from destination metadata whenever possible.
- Lakehouse catalogs, table formats, and governance tools are the preferred location for auditing information.
- The framework may emit logs, metrics, and load statistics.
- Operational logging for troubleshooting is allowed, but is not an auditing system.

Vision:
Describe ingestion, don't implement plumbing.
